# Devices Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The phone app pairs with ScadBuddy as a device. Pages, flows and the assistant then call its four methods: `nfc.read`, `nfc.write`, `code.scan` and `camera.capture`. Each call streams its events and ends with a stored read.

**Architecture:** A new Go package `tools/go/core/internal/devices` owns the pairing, the tokens, the calls and the device reads. It builds no transport of its own. Calls reach the device as bus events on the realtime socket it subscribes to. Events and results come back over HTTP. Bytes go through the blob store, and approvals through pending actions. A call's events, and the call itself on its way to the pod that holds the socket, are events on ScadBuddy's existing event stream (`internal/bus`). That stream has the log, the retention, the replay and the topic subscriptions the realtime socket serves. Nothing new is added for events. The app (`app/ScadBuddy`) pairs through a `scadbuddy://pair` link, keeps the token in `SecureStorage`, holds the socket while it is in front, and answers calls with its native NFC and camera.

**Tech Stack:** Go (core, pgx, the realtime package's RFC 6455 server), Postgres, .NET MAUI Android, React (the Devices page).

**Spec:** `docs/superpowers/specs/2026-11-27-devices-design.md`

## Global Constraints

- Only four capabilities: `nfc.read`, `nfc.write`, `code.scan`, `camera.capture`. ScadBuddy is not a device platform.
- Pairing code: at least 128 random bits. Only its hash is stored. It is single-use and expires in 10 minutes.
- Device token: at least 256 random bits. Only its hash is stored. It expires after 1 hour idle, and each authenticated device request moves the expiry to now + 1 hour. Hard cap: 30 days from pairing. Both values are settings.
- Heartbeat every 30 s. A call's deadline is at most 2 minutes.
- Device-token routes (the pairing claim, the heartbeat, a call's events and result, the device upload, and the realtime socket's device path) check the token in every auth mode. Person routes follow the global mode. Never `SCADBUDDY_AUTH_MODE=enforce` on prod.
- A Bambu tag is never written. Core refuses it by the shape of the args: `nfc.write` takes NDEF records only, with no raw block, sector or key, so core never asks for a MIFARE sector write. Core does not check a tag's UID. The device refuses a Bambu tag it meets.
- Bytes never go in an event or a result, and never as base64 in JSON (#2479). Tag dumps go as kind `tag_dump`, photos as kind `scan_image`.
- One new migration file in `backend/scadbuddy/migrations/`, named `$(date -u +%Y%m%dT%H%MZ)_devices.sql`.
- New backend code is Go. Only core and the API hold SQL.
- An outward call made by the assistant or a flow needs a pending action. A person's own click on a page is the approval.

## Review Focus

1. **Two pods.** The caller's request lands on pod A, and the device's realtime socket is on pod B. The call still reaches the device, and its events reach the caller (Task 4, `TestCallAcrossPods`).
2. **The device goes away in the middle of a call.** The call ends with outcome `offline` once its deadline passes. It never hangs (Task 4, `TestCallDeviceGoneMidCall`).
3. **Revoke while online.** Revoking a device closes its realtime socket at once. Its next heartbeat, event, upload or reconnect gets 401 (Task 3, `TestRevokeClosesSocket`).
4. **Old or reused codes.** A pairing code used twice, or used after 10 minutes, gets 410. It makes no device (Task 2, `TestPairCodeSpentOnce`).
5. **A hostile result.** A device's result names a blob the device did not upload, or a kind that does not match its method. Core refuses it. It writes no `device_reads` row, and the call ends with `error` (Task 5, `TestResultRefusesForeignBlob`).

### Task 1: Tables

**Files:**
- Create: `backend/scadbuddy/migrations/<UTC>_devices.sql`
- Test: `tools/go/core/internal/devices/schema_test.go`

**Interfaces:**
- Produces these tables:
  - `devices` (id uuid pk, owner text, name text, model text, app_version text, capabilities text[], created_at, last_seen_at, revoked_at);
  - `device_pairings` (code_hash bytea pk, owner text, created_at, expires_at, spent_at, device_id uuid null);
  - `device_tokens` (token_hash bytea pk, device_id uuid fk, created_at, expires_at, hard_cap_at, revoked_at);
  - `device_calls` (id uuid pk, device_id, caller text, caller_kind text, method text, args jsonb, timeout_s int, outcome text null, result jsonb null, created_at, ended_at);
  - `device_reads` (id uuid pk, device_id, call_id, at, kind text check in ('nfc','photo'), uid text null, tech text null, blob_key text, media_type text, complete bool, missing_blocks int[]).
- `args` and `result` are each at most 4 KiB, by a `CHECK (octet_length(x::text) <= 4096)`. A call is also refused with `413 args_too_large` when its `device.call_requested` event would not fit the bus (`bus.Fits`, `PayloadMax`, 4000 bytes): `bus.Publish` drops a larger event, and the call would be lost. So args under 4 KiB can still be refused, and no `device_calls` row is written.

### Task 4: Calls and their events

**Files:**
- Create: `tools/go/core/internal/devices/calls.go`
- Test: `tools/go/core/internal/devices/calls_test.go`

**Interfaces:**
- `POST /api/v1/devices/{id}/calls {method, args, timeout_s}` answers `202 {call_id}`. It answers `409 {"error":"offline"}` when `Store.Online` is false (no heartbeat in 75 s), and `422` for a method the device did not announce. With `?wait=true`, it holds the request until the result (200) or the deadline (504).
- `GET /api/v1/devices/calls/{id}` answers `{call, events: [...], result}`. Its events are read from the event log by the topic `device:call:<id>`. A page that follows a call live also subscribes to that topic on the realtime socket.
- Each posted event is published with `bus.Publish(ctx, pool, "device."+kind, ...)`, with the fields `call`, `device` and the event's data, and the topics `device:<device id>` and `device:call:<call id>`. Kinds: `device.tag_found`, `device.tag_progress`, `device.tag_lost`, `device.call_done`, `device.call_failed`. An event whose kind is not one of these is refused. `retention_seconds` is 7 days.
- A call is published as `device.call_requested` with the topic `device:<device id>`, with the fields `call`, `method`, `args` and `deadline`. The device's realtime socket delivers it.
- An event's `data` is at most 1024 bytes (`422` above it), so a posted event always fits the bus. Core still checks each event with `bus.Fits` before it logs any of them, and answers `413 event_too_large` for one that does not fit.
- Device routes: `POST /api/v1/devices/calls/{id}/events {events: [{kind, data}]}` (at most 20 per request) and `POST /api/v1/devices/calls/{id}/result {outcome: "done"|"error", result}`. Only the call's own device may post them, and only while the call is open.
- `timeout_s` defaults to 60 and is at most 120.

- [ ] **Step 1:** Write these tests:

  - `TestEventFrameUnknownKindRefused`.
  - `TestCallAcrossPods` (Review Focus 1): the call is made on one router, and the device's realtime socket is on a second router over the same testdb. The call still arrives.
  - `TestCallDeviceGoneMidCall` (Review Focus 2).

Only the device's owner, the call's caller, or a delegate service for the person it made the call for (`?on_behalf_of=`) reads a call and follows its topic.

  - `TestEventDataTooLarge`: an event whose `data` is over 1024 bytes gets `422`, and no event of the request is logged.
